# Git Workflow

## Цель

История репозитория должна быть читаемой, предсказуемой и полезной для ревью. Мы не делаем "коммит всего подряд". Каждый коммит должен отвечать на вопрос: **зачем было сделано это изменение**.

## Основные правила

- один коммит = одна логическая идея;
- не смешивать инфраструктуру, рефакторинг и новую фичу без необходимости;
- коммитить маленькими порциями, чтобы можно было легко откатить или понять изменение;
- не коммитить секреты, `.env`, локальные дампы, временные файлы и артефакты сборки;
- перед коммитом проверять, что staged changes действительно относятся к одному смысловому изменению.

## Формат сообщений

Используем стиль `Conventional Commits`.

Шаблон:

```text
type(scope): short summary
```

Примеры:

- `docs(project): define initial orderflow architecture`
- `chore(repo): initialize git standards and ignore rules`
- `feat(order): create order creation endpoint`
- `feat(inventory): reserve stock on order created`
- `fix(payment): enforce idempotency on retry`
- `refactor(auth): extract jwt validation module`
- `test(order): cover failed payment saga path`

## Разрешенные типы

- `feat` - новая функциональность;
- `fix` - исправление бага или нежелательного поведения;
- `refactor` - изменение структуры без новой функциональности;
- `docs` - документация;
- `test` - тесты;
- `chore` - инфраструктурные и служебные изменения;
- `build` - сборка, docker, CI/CD, tooling;
- `perf` - оптимизация производительности.

## Scope для этого проекта

Предпочтительные `scope`:

- `repo`
- `project`
- `gateway`
- `auth`
- `catalog`
- `order`
- `inventory`
- `payment`
- `notification`
- `analytics`
- `infra`
- `observability`

## Когда делить на несколько коммитов

Нужно разбивать изменения, если в одном наборе есть:

- документация и код;
- инфраструктура и бизнес-логика;
- рефакторинг и новая фича;
- механические переименования и смысловые изменения.

## Мини-чеклист перед коммитом

Перед коммитом убедиться, что:

- сообщение отражает причину изменения;
- в staged нет лишних файлов;
- изменение можно объяснить одним коротким абзацем;
- коммит не тянет за собой несвязанные правки.

## Правило для начальной стадии проекта

Пока мы строим foundation, лучше делать коммиты чаще и меньше:

- `docs(...)` для архитектурных решений;
- `chore(repo|infra)` для структуры, git и локального окружения;
- `feat(...)` только когда появляется реальное поведение системы.
